模型家族全景：从架构选择看每个模型的"性格"

不是"哪个模型最强"，而是"哪个模型的性格适合你的场景"。架构决定性格，性格决定场景。

为什么 Dense 和 MoE 的分水岭最重要​

2025-2026 年的大模型市场有一个最明显的分化：有的公司选择把 Dense 做到极致，有的公司选择走 MoE 路线。这不是技术路线之争，而是产品哲学之争。

Dense 阵营（所有参数每个 token 都激活）:
  Claude 系列 (Anthropic)
  GPT 系列 (OpenAI)
  Gemini 2.5 (Google, 早期版本)

MoE 阵营（每个 token 只激活一小部分参数）:
  Llama 4 (Meta)
  DeepSeek V3/V4
  Qwen3 / Qwen3.5
  Kimi K2 / K2.5
  Gemini 3+ (Google, 后期版本)
  GLM-5 (Zhipu)
  Mistral Large 3

一行话： Dense 模型的推理延迟更可预测，MoE 模型的参数效率更高。但这不意味着谁更好——它们适合的场景完全不同。

七大模型家族的架构与性格​

Claude（Anthropic）— 克制的工匠​

架构选择：Dense Transformer + 混合推理模式

在所有主流模型厂商都在转向 MoE 的时候，Anthropic 坚持用 Dense 架构。原因不是技术落后，而是产品哲学：

Dense 架构的核心优势:
  1. 可预测性：每个 token 的计算路径一致，延迟稳定
  2. 代码质量：Claude Opus 系列在编码 benchmark 上长期领先
  3. 指令跟随：Dense 模型对复杂指令的理解更一致
  4. 安全边界：Anthropic 的 Constitutional AI 训练方式与 Dense 架构配合更好

代价:
  1. 推理成本高（所有参数都要计算）
  2. 参数规模天花板比 MoE 低
  3. 上下文窗口上限受限（200K tokens）

它擅长什么：

场景原因
编码（重构、Agent 工作流）Dense 架构下代码理解和生成的质量最高
长文档分析200K 上下文内的信息提取和总结能力强
安全敏感应用内置 Constitutional AI，输出可控性好
复杂指令任务多步骤、多约束的指令跟随能力突出

它不擅长什么： 超长上下文（超过 200K）、极致低成本、本地部署（不开源）。

适合谁： 需要高质量代码生成、文档分析、安全可控的企业应用。

GPT（OpenAI）— 均衡的全能选手​

架构选择：Dense Transformer + 可调推理深度

OpenAI 的策略是把 GPT-5 做成"什么都好"的模型，用推理深度（thinking toggle）来覆盖从快速聊天到深度推理的全场景。

GPT 系列的差异化:
  1. 云边混合推理：部分推理在设备端执行，降低延迟
  2. Thinking Toggle：用户可调思考深度，不用切换模型
  3. 上下文窗口：400K tokens（272K 输入 / 128K 输出）
  4. 生态系统：最完善的 API、工具链、第三方集成

它擅长什么：

场景原因
通用聊天GPT-5.5 在日用聊天上表现最自然
多模态原生支持文本、图像、音频，统一处理
企业集成API 生态最成熟，第三方工具支持最广
可调节推理深度简单问题不 thinking 快速回答，复杂问题 deep thinking

它不擅长什么： 极致编码质量（略逊于 Claude Opus）、自部署（不开源）、极致低成本（旗舰模型价格高）。

适合谁： 需要广泛集成能力、多模态、可调推理深度的通用应用。

Gemini（Google）— 上下文之王​

架构选择：从 Dense 到 MoE 的演进（Gemini 3+ 是 Sparse MoE）

Google 的策略很清晰：把上下文窗口做到极致，用 MoE 降低大模型的推理成本。

Gemini 的差异化:
  1. 100 万 -200 万 token 上下文窗口（业界最大）
  2. 原生多模态：文本、视觉、音频在同一个 token 空间
  3. Deep Think 模式：推理时的扩展推理能力
  4. Gemini 3 Pro 是 Sparse MoE：万亿参数，但推理成本可控

它擅长什么：

场景原因
全代码库分析1M+ 上下文可以直接吞下一个完整项目
长文档/论文整本书或整篇论文的分析和摘要
研究/科学Gemini 3.1 Pro 在推理 benchmark 上领先
多模态融合文本、图像、音频的统一处理

它不擅长什么： 代码生成的质量不如 Claude Opus、生态系统不如 GPT 成熟、消费者版本可能受限于上下文窗口。

适合谁： 需要处理超长上下文（完整代码库、长篇文档）、多模态融合的应用。

DeepSeek — 价格颠覆者​

架构选择：DeepSeekMoE + MLA（多头潜在注意力）

DeepSeek 的杀手级能力不是技术最先进，而是用极低的成本做到了前沿的质量。

DeepSeek 的差异化:
  1. DeepSeekMoE: 671B 总参数，但每个 token 只激活 ~37B
  2. MLA（Multi-Head Latent Attention）: 压缩 KV Cache 的注意力变体
     这是 DeepSeek 自研的注意力机制，显存效率比标准 MHA 高
  3. 定价策略：$0.014/1M tokens（缓存命中时），是 OpenAI 的 1/100
  4. 中英双语：中文能力在所有前沿模型中数一数二

MLA 的一行解释： 标准 MHA 的 KV Cache 大小和 head_dim 成正比。MLA 用一个"潜在维度"压缩 KV 表示，显存占用降低但质量损失极小。这对 MoE 模型特别重要——因为 MoE 本身就要加载大量 Expert 权重，KV Cache 的优化能直接缓解显存压力。

它擅长什么：

场景原因
成本敏感的高量应用价格比 Western 模型低 10-100 倍
中文应用中英双语能力强
批量处理低成本支持大规模离线处理
编码R1 和 V4 的编码能力接近前沿水平

它不擅长什么： 峰值延迟（高峰期排队）、生态系统（工具链不如 GPT 成熟）、地缘政治考虑（部分组织有合规限制）。

适合谁： 需要前沿质量但预算有限的团队、中文市场应用、批量处理场景。

Llama（Meta）— 自部署的首选​

架构选择：从 Dense 到 MoE（Llama 4 是第一个 MoE Llama）

Llama 的核心价值不是质量最强，而是"你自己的 GPU 上能跑"。

Llama 的差异化:
  1. 开源权重：可下载、可微调、可自部署
  2. Llama 4 是 MoE：400B 总参数 / 17B 激活参数，128 experts
  3. 原生多模态：文本 + 图像
  4. 生态系统：HuggingFace、vLLM、llama.cpp 全面支持

它擅长什么：

场景原因
隐私敏感部署数据不出自己的服务器
自定义微调开源权重，想怎么调就怎么调
成本可控（长期）一次部署，无限调用，没有 API 费用
生态集成社区支持最广，工具链最成熟

它不擅长什么： 绝对质量（略逊于商用旗舰）、开箱即用体验（需要自己搭建基础设施）、多语言（英文为主）。

适合谁： 需要数据主权、需要定制微调、有 GPU 基础设施的团队。

Qwen（阿里巴巴）— 最宽的模型家族​

架构选择：Dense + MoE 双路线，从 0.6B 到 1T+

Qwen 的策略不是"做一个最好的模型"，而是"每个尺寸都提供一个好模型"。

Qwen 的差异化:
  1. 最宽的范围：0.6B（手机能跑）到 480B MoE（云端旗舰）
  2. 最强的 CJK 覆盖：中文、日文、韩文
  3. Qwen3-Coder: 专用的编码 MoE 变体
  4. Qwen3-Next 架构：80B 总参数但仅 3B 激活（极致 MoE 效率）
  5. 端侧部署：Qwen3.5 可以在 iPhone 上运行

它擅长什么：

场景原因
中文/亚洲市场CJK 语言能力最强
边缘部署0.6B-4B 型号适合手机和 IoT
多尺寸需求同一个家族，从手机到云端都有对应型号
编码Coder 系列有专门的编码优化

它不擅长什么： 英文前沿推理（英语 benchmark 略逊于 Claude/GPT）、部分变体的成熟度不如旗舰。

适合谁： 亚洲市场应用、需要端侧到云端的全覆盖、多语言场景。

Kimi（月之暗面）— 持久 Agent​

架构选择：MoE（1T 总参数 / 32B 激活参数）

Kimi 的定位很独特：它是目前最擅长"持续工作"的模型。

Kimi 的差异化:
  1. MoE 架构：1T 参数但仅 32B 激活，推理成本可控
  2. Agent Swarm：K2.6 支持最多 300 个子 Agent 协作
  3. 持久编码：13 小时连续编码会话（不是 13 小时延迟，是 13 小时持续工作）
  4. 256K 上下文窗口

它擅长什么：

场景原因
长期开发会话13 小时持续编码，适合大规模重构
多 Agent 协作Agent Swarm 支持复杂的多角色协作任务
中文编码中英双语编码能力

它不擅长什么： 生态系统较新、英文社区支持有限。

适合谁： 需要长周期编码任务、多 Agent 协作的场景。

架构差异如何影响部署决策​

显存对比：同样"大"的模型，显存需求完全不同​

Dense 模型（以 Claude 级别为例，假设 ~200B 参数）:
  权重显存: 200B × 2 bytes (FP16) = 400 GB
  KV Cache: 取决于 batch 和 context length
  推理策略: 必须多卡并行（Tensor Parallelism）

MoE 模型（以 DeepSeek V3 为例，671B 总参数 / 37B 激活）:
  权重显存: 671B × 2 bytes = 1342 GB（全部 Expert 需要加载）
  KV Cache: 由于 MLA 压缩，比同级别 Dense 模型小 ~30%
  激活计算: 仅 37B 的 FLOPs（接近 37B Dense 模型的计算量）
  推理策略: Expert 分布式并行 + KV Cache 优化

关键洞察:
  MoE 的显存需求由总参数决定（所有 Expert 都要加载到显存）
  MoE 的计算量由激活参数决定（只有 Top-K Expert 参与计算）
  Dense 的显存和计算量都由同一个数字决定（总参数 = 激活参数）

延迟可预测性对比​

Dense 模型（Claude / GPT）:
  每个 token 的计算路径一致
  → 延迟 = f(input_length) + g(output_length)
  → 可预测、可规划

MoE 模型（Llama 4 / DeepSeek / Qwen）:
  每个 token 的 Expert 选择不同
  → 延迟 = f(input_length) + g(output_length) + h(router_skew)
  → 总体可预测，但 Expert 负载不均衡时会有波动

影响:
  如果你的应用需要严格的延迟 SLA（如 <500ms TTFT）
  Dense 模型更容易满足
  MoE 模型需要额外的 Router 监控和负载均衡

Thinking 模式对比​

模型Thinking 机制最大 Thinking Tokens控制方式
Claude 4.x+Extended Thinking32KAPI 参数控制
GPT-5.xThinking Toggle可调深度用户界面滑块

选型决策树​

一个实用的"多模型路由"策略​

生产环境中最成熟的方案不是选一个模型，而是用路由把不同模型组合起来：

请求进来 → 分类器判断类型 → 路由到合适的模型

分类维度:
  1. 任务类型: 编码 / 写作 / 推理 / 多模态 / 分类
  2. 复杂度: 简单（直接回答） / 中等（短思考） / 复杂（深度推理）
  3. 延迟要求: 实时（<500ms） / 普通（<3s） / 异步（>10s）
  4. 成本敏感度: 高 / 中 / 低

路由示例:
  编码 + 复杂 + 异步 → Claude Opus（质量优先）
  编码 + 简单 + 实时 → Codestral 或 Qwen3-Coder（速度优先）
  写作 + 中等 + 普通 → GPT-5.5（平衡）
  分类 + 简单 + 实时 → GPT-5 Nano 或 Qwen3-0.6B（成本优先）
  长文档 + 任意 → Gemini 3 Pro（上下文优先）
  中文 + 中等 + 普通 → Qwen3 或 DeepSeek（语言优先）
  批量处理 + 任意 → DeepSeek V3（成本优先）

多模型路由的核心原则： 不是每个请求都用最强的模型，而是每个请求都用最合适的模型。

面试视角​

常考问题​

  1. "Dense 和 MoE 各有什么优缺点？你会在什么场景下选择哪种架构？"

    回答框架：

    • Dense：所有参数每个 token 都计算。优点是可预测、延迟稳定、部署简单。缺点是推理成本高，参数规模有天花板
    • MoE：总参数大，每个 token 只激活 Top-K 个 Expert。优点是参数效率高、知识容量大。缺点是部署复杂（需要 Expert 并行）、延迟不如 Dense 可预测
    • 选择：严格延迟 SLA 的场景选 Dense，预算有限但需要前沿质量的场景选 MoE，需要自部署且有显存限制的场景看 MoE 的激活参数是否满足

  2. "为什么 DeepSeek 能把价格做到比 OpenAI 低 100 倍？"

    回答框架：

    • MoE 架构：671B 参数但仅激活 37B，计算成本低
    • MLA 注意力机制：KV Cache 压缩，显存效率高
    • 训练效率高：用更少的计算量达到相近的效果
    • 中国的 GPU 成本和定价策略差异
    • 但要注意：低价不等于低质，DeepSeek 的编码和推理能力接近前沿水平

  3. "如果让你为一个生产级编码 Agent 选型，你会怎么考虑？"

    回答框架：

    • 编码质量优先：Claude Opus 是最佳选择（编码 benchmark 领先）
    • 如果有成本约束：用 DeepSeek V3 做日常编码，Claude Opus 做关键重构
    • 如果需要长周期任务：考虑 Kimi K2.6（13 小时持续编码）
    • 最终推荐：多模型路由——日常编码走 DeepSeek（便宜），关键代码审查走 Claude Opus（质量），批量代码生成走 DeepSeek（成本）

  4. "MLA 是什么？它和标准 MHA 的区别在哪里？"

    回答框架：

    • MHA 的 KV Cache 大小和 attention head dimension 成正比
    • MLA 用一个"潜在维度"（latent dimension）压缩 KV 表示
    • KV Cache 显存降低 ~30%，但质量损失极小
    • 这是 DeepSeek 自研的注意力变体，特别适合 MoE 模型（因为 MoE 本身就要加载大量 Expert 权重，KV Cache 优化能缓解显存压力）

  5. "GPT 和 Claude 都支持"思考模式"，它们的实现方式有什么不同？"

    回答框架：

    • Claude 的 Extended Thinking：固定模式，最多 32K thinking tokens，通过 API 参数控制
    • GPT-5 的 Thinking Toggle：可调深度，用户用滑块控制思考深度
    • 两者都基于 chain-of-thought 训练，但控制粒度不同
    • GPT 的方式更灵活（可以微调思考深度），Claude 的方式更精确（可以指定最大 thinking tokens）
