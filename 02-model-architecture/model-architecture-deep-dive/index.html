DeepSeek V3 — MoE + MLA 的成本颠覆术​

架构规格​

项目数值
总参数671B
激活参数37B（每个 token）
Transformer 层数61 层
隐藏维度7,168
训练精度FP8 混合精度

核心创新 1：DeepSeekMoE 的细粒度 Expert 切分​

DeepSeekMoE 与传统 MoE 的关键区别在于Expert 粒度：

传统 MoE（如 Mixtral 8×7B）:
  8 个 Expert，每个 Expert 是一个完整的 FFN（~7B 参数）
  Top-2 路由 → 每个 token 经过 2 个 Expert
  激活参数: ~13B

DeepSeekMoE:
  256 个细粒度 Expert（每个 Expert 很小）
  Top-8 路由 + 1 个 Shared Expert
  激活参数: ~37B

细粒度 Expert 的优势:
  1. Router 选择更精细 → token 匹配更精准
  2. Expert 专业化程度更高 → 每个 Expert 学到特定模式
  3. 负载更均衡 → 256 个 Expert 分担 8 个路由目标
  4. 训练效率更高 → 细粒度 Expert 更容易并行化

核心创新 2：MLA 的 KV Cache 压缩​

MLA（Multi-Head Latent Attention）是 DeepSeek 自研的注意力变体，核心思路：

标准 MHA 的 KV Cache:
  每层: 2 × num_heads × head_dim × bytes
  Llama 3 70B (80 heads, 128 dim): 每 token 每层 ~40 KB

MLA 的 KV Cache:
  将 K 和 V 投影到一个"潜在维度"（latent dimension）
  潜在维度 << 原始 head_dim（通常压缩 3-5 倍）
  每层: 2 × num_heads × latent_dim × bytes
  压缩后: 每 token 每层 ~10-13 KB

显存节省: ~30-50%
质量损失: < 1%（在标准 benchmark 上不可测）

MLA 对 MoE 模型特别重要：MoE 本身就要加载 671B 的 Expert 权重到显存，KV Cache 的优化能直接缓解显存压力，让更大的 batch size 成为可能。

核心创新 3：FP8 训练​

DeepSeek V3 是全球首个在大规模训练中使用 FP8 精度的前沿模型：

FP8 格式: 8-bit 浮点数（1 sign + 4 exponent + 3 mantissa）
相比 FP16: 显存减半、带宽减半
相比 FP32: 显存 1/4、带宽 1/4

关键挑战:
  FP8 的动态范围很小 → 梯度容易溢出或下溢
  DeepSeek 的解法: 每 tensor 每 step 动态调整缩放因子

效果:
  用约 1/3 的 compute 量达到相近效果
  这是 DeepSeek 能把 API 价格做到 $0.014/1M tokens 的核心原因之一

部署视角​

DeepSeek V3 在 H100 上的部署要点:

显存需求:
  权重: 671B × 2 bytes (FP16) = 1,342 GB
  必须分布在 16+ 张 H100 上（每张 80GB）

KV Cache:
  MLA 压缩后，每 token 每层 ~10 KB
  比同等规模 Dense 模型节省 ~40%

吞吐:
  batch=1: ~15-20 token/s
  batch=64: ~800-1000 token/s（受 Expert 并行效率影响）

成本:
  API 价格 $0.014/1M tokens (cache hit)
  自部署: 需要 16+ H100，前期投入高但调用无额外成本

它的优势从何而来​

优势根源
极低价格FP8 训练降低训练成本 + MoE 降低推理 FLOPs
中英双语强训练数据中中文比例高 + 高质量中文语料
编码接近前沿671B 总参数的知识容量 + 细粒度 Expert 的专业化
长上下文可行MLA 压缩 KV Cache 使长上下文显存可控

Llama 4 — 极致稀疏的 MoE 先锋​

架构规格​

模型总参数激活参数ExpertsRouting共享 Expert
Scout109B17B16Top-1是 (1)
Maverick400B17B128Top-1是 (1)
Behemoth~2T288B16—是

核心创新 1：Top-1 路由的极致稀疏性​

Llama 4 的 MoE 路由策略是极致稀疏的：

大多数 MoE 模型:
  Mixtral 8×7B: Top-2（每个 token 经过 2 个 Expert）
  DeepSeek V3: Top-8 + Shared（每个 token 经过 8+1 个 Expert）

Llama 4 Maverick:
  Top-1 Routing: 每个 token 只经过 1 个 Routed Expert + 1 个 Shared Expert
  128 个 Expert，但每次只激活 2 个

为什么 Top-1 能工作?
  1. Shared Expert 提供稳定的基础能力（类似 Dense 模型的 FFN）
  2. 128 个 Expert 的细粒度切分让每个 Expert 足够专精
  3. Router 在 128 个选项中选择 1 个 → 选择精度足够高
  4. 交替 Dense/MoE 层的设计平衡了效率和表达能力

核心创新 2：交替 Dense + MoE 层​

Llama 4 的层结构:

Layer 1: Dense FFN（所有参数激活）
Layer 2: MoE FFN（Top-1 + Shared）
Layer 3: Dense FFN
Layer 4: MoE FFN
...

交替设计的优势:
  1. Dense 层保证基础表达能力稳定
  2. MoE 层提供大规模参数带来的知识容量
  3. 训练更稳定（Dense 层作为"安全网"）
  4. 推理效率接近纯 MoE（MoE 层占多数）

对比:
  纯 Dense 模型: 训练慢、推理贵
  纯 MoE 模型: 训练不稳定、Expert 易"饿死"
  交替 Dense+MoE: 两全其美

核心创新 3：iRoPE（Image-Enhanced RoPE）​

Llama 4 是原生多模态的，其位置编码做了图像增强：

标准 RoPE（用于纯文本）:
  用旋转位置编码建模 token 在序列中的相对位置

iRoPE:
  图像 patch 和文本 token 共享同一个 RoPE 空间
  图像被切分为 patch，每个 patch 作为独立的 token 输入
  RoPE 同时编码文本 token 的序列位置和图像 patch 的 2D 空间位置

效果:
  不需要额外的图像编码器（如 CLIP Vision Encoder）
  文本和图像在同一个 token 空间交互

部署视角​

Llama 4 Maverick 部署要点:

显存需求:
  权重: 400B × 2 bytes = 800 GB
  需要 10+ 张 H100 80GB

路由开销:
  Top-1 路由选择 128 个 Expert → 额外 ~5% 计算开销
  但 Shared Expert 始终激活 → 路由决策不影响 Shared 路径

负载不均衡风险:
  Top-1 路由容易出现 Expert 负载倾斜
  需要监控每个 Expert 的激活频率
  偏差超过 2x 时考虑调整 load balancing loss 权重

吞吐:
  batch=1: ~20-25 token/s
  batch=32: ~500-600 token/s

它的优势从何而来​

优势根源
开源可自部署Meta 的开源战略，权重可下载
训练效率提升 4x交替 Dense+MoE + Top-1 路由
400B 参数仅激活 17B128 Expert 的细粒度切分
多模态原生iRoPE 统一文本和图像的位置编码

Qwen3.5 — 混合注意力的架构革命​

架构规格​

模型总参数激活参数注意力类型上下文窗口
Qwen3-235B-A22B235B22BGQA + 标准 FFN128K
Qwen3.5-397B-A17B397B17BGated DeltaNet + Gated Attention260K+
Qwen3.5-27B27B27BDense128K
Qwen3-Next (80B-A3B)80B3B混合128K

核心创新：Gated DeltaNet + Gated Attention 混合架构​

Qwen3.5 在注意力机制上做了最激进的改变：

标准 Transformer:
  每一层都用 Self-Attention（O(N^2) 复杂度）

Qwen3.5 混合注意力:
  Gated DeltaNet: 线性注意力变体，O(N) 复杂度
    - 用状态空间模型（SSM）的思想替代部分 Attention
    - 对"不需要精确 token-to-token 匹配"的场景极高效
  Gated Attention: 标准 Attention 的门控版本
    - 在需要精确 token 匹配的场景保留完整 Attention
    - 通过门控动态决定用哪种注意力

动态路由:
  每一层都有一个门控网络，决定该层用 DeltaNet 还是 Attention
  训练时联合优化 → 模型自己学习哪些层用哪种注意力

效果:
  计算效率提升 ~80%（相比纯 Attention）
  长上下文推理速度提升 3-5x
  质量损失极小（在标准 benchmark 上几乎持平）

这意味着 Qwen3.5 在架构层面就已经不是纯 Transformer 了。它是混合了状态空间模型（SSM）和注意力机制的新型架构。

Qwen3-235B-A22B 的 MoE 设计​

Qwen3 的 MoE 规格:
  235B 总参数 / 22B 激活参数
  94 层 Transformer
  Top-K 路由（学习得到的门控）

对比 DeepSeek V3:
  DeepSeek: 61 层, 256 Expert, Top-8, 671B/37B
  Qwen3: 94 层, Expert 数量较少, Top-K 较小, 235B/22B

Qwen3 的选择:
  更多层数 → 更深的网络，表达能力更强
  更少的 Expert → 部署更简单，Expert 并行开销更小
  更小的激活参数（22B vs 37B）→ 推理更便宜

部署视角​

Qwen3.5-397B-A17B 部署要点:

混合注意力的显存影响:
  DeltaNet 部分不需要存储 O(N^2) 的 attention matrix
  长上下文（>100K tokens）时，显存比纯 Attention 节省 50-70%

激活参数仅 17B:
  FLOPs 接近 17B Dense 模型
  这意味着在单张 H100 上也能跑（如果 Expert 能放下）

实际部署:
  需要 5+ 张 H100 80GB
  batch=1: ~25-30 token/s（受益于线性注意力）
  batch=32: ~600-800 token/s

它的优势从何而来​

优势根源
长上下文推理快混合注意力：DeltaNet 部分 O(N) 复杂度
CJK 语言能力强训练数据中 CJK 比例高 + 专用 tokenizer
端侧可部署0.6B-8B 小模型系列，Qwen3.5 可在 iPhone 上跑
编码专用模型Qwen3-Coder 有专门的编码 Expert

Kimi K2.5 — 万亿参数的 Agent 引擎​

架构规格​

项目数值
总参数1T
激活参数32B
训练数据~15T tokens（多模态混合）
上下文窗口256K tokens
架构MoE（混合）

核心创新 1：Agent Swarm 的架构支撑​

Kimi K2.5 的 Agent Swarm 不是"应用层"的东西，而是有模型层面的架构支撑：

Agent Swarm 架构:
  Orchestrator Agent:
    - 一个专门的"编排"Expert 负责任务分解
    - 将复杂目标分解为子任务 DAG
  Worker Agents:
    - 每个子任务由独立的 Expert 组处理
    - 支持最多 300 个子 Agent 并行（K2.6）
  Shared Memory:
    - 256K 上下文窗口作为共享工作空间
    - 所有子 Agent 的中间结果都在同一个 KV Cache 中

为什么 MoE 架构天然适合 Agent Swarm?
  1. MoE 的 Expert 天然就是"专业化子网络"
  2. 不同的子任务可以被路由到不同的 Expert 组
  3. 1T 总参数提供了足够的"专业知识储备"
  4. 32B 激活参数保证了推理成本可控

对比:
  Dense 模型做 Agent Swarm: 所有 Expert 共享同一组参数
    → 任务间干扰大，容易"串台"
  MoE 模型做 Agent Swarm: 不同任务路由到不同 Expert
    → 任务隔离好，并行质量高

核心创新 2：13 小时持续编码​

13 小时持续编码的关键:
  1. MoE 的 Expert 专业化 → 编码相关的 Expert 被高频激活
    → 编码质量在长时间会话中不衰减
  2. 256K 上下文窗口 → 足够容纳整个代码库的历史
  3. 32B 激活参数 → 足够大以维持编码质量，又足够小以控制成本

技术实现:
  持续的 KV Cache 管理（滑动窗口 + 关键信息保留）
  定期压缩历史上下文（保留决策理由，删除中间推理）
  Expert 激活模式稳定（编码任务 → 编码 Expert 持续激活）

部署视角​

Kimi K2.5 部署要点:

显存需求:
  权重: 1T × 2 bytes = 2,000 GB
  需要 25+ 张 H100 80GB

Agent Swarm 模式的资源消耗:
  每个子 Agent 需要独立的 KV Cache 空间
  300 子 Agent → 需要大规模 KV Cache 管理
  建议: 使用 Prefill-Decode 分离架构
    - Prefill: 少量 GPU 处理任务分解
    - Decode: 大规模 GPU 集群处理子 Agent 执行

吞吐:
  单 Agent: ~10-15 token/s
  Agent Swarm: 取决于子 Agent 并行度

它的优势从何而来​

优势根源
长时间编码MoE Expert 专业化 + 大上下文 + KV Cache 管理
多 Agent 协作1T 参数提供的专业知识储备 + Expert 天然隔离
中文编码中文训练数据 + 编码专用 Expert

Gemini 3 Pro — 万亿级 MoE 的上下文王者​

架构规格（基于公开信息估计）​

项目估计值
总参数~3-7.5T（未官方披露）
激活参数~15-20B（估计）
上下文窗口100 万 -200 万 tokens
架构Sparse MoE Transformer
多模态原生（文本、视觉、音频统一 token 空间）

核心创新 1：百万级上下文窗口的工程实现​

100 万 token 上下文的技术挑战:

1. Attention 计算:
   标准 Attention: O(N^2) = O(1,000,000^2) = 10^12 次计算
   → 不可行

   Gemini 的解法:
   - 滑动窗口 Attention + 全局 Memory Tokens
   - 或 Linear Attention 变体
   - 将 attention matrix 分块计算

2. KV Cache:
   1M tokens × 每 token 每层 KV
   标准: 1M × 2 × 80 × 128 × 2 bytes × N_layers ≈ 数 TB
   → 不可能全缓存

   Gemini 的解法:
   - MoE 架构降低层间通信开销
   - KV Cache 分块管理（近期 token 全缓存，远距离 token 压缩）
   - 可能使用了类似 Ring Attention 的分布式 attention

3. 位置编码:
   标准 RoPE 在 1M+ 长度下精度下降
   Gemini 可能使用了:
   - 扩展 RoPE（增加基频）
   - 或专用的长距离位置编码方案

核心创新 2：原生多模态的统一 token 空间​

传统多模态:
  图像 → CLIP Vision Encoder → 图像 embedding → 投影到文本空间
  → 两套独立的编码器和 token 空间

Gemini 3 Pro:
  图像 patch、音频 frame、文本 token 都在同一个 token 空间
  同一个 Transformer 处理所有模态
  同一个 Attention 机制跨模态交互

优势:
  - 跨模态的 attention 是"天然"的（不需要额外的融合层）
  - 可以"看到代码"（图像中的代码截图 → 直接理解）
  - 可以"听到指令"（音频输入 → 直接处理）

核心创新 3：Meta-Controller Layer​

Gemini 3 Pro 有一个额外的 Meta-Controller 层:
  -  supervisory agent 负责将高层目标分解为子任务 DAG
  -  类似于 Agent Swarm 的 orchestrator，但内置在模型架构中
  -  支持 Deep Think 模式（扩展推理）

这与外部 Agent 框架（LangGraph 等）的区别:
  外部框架: 应用层编排多个独立模型
  Meta-Controller: 模型内部的自编排
  → 延迟更低，一致性更高

部署视角​

Gemini 3 Pro 部署要点:

由于 Google 未公开详细规格:
  总参数估计 3-7.5T → 需要 40+ 张 H100 80GB（如果自部署）
  激活参数 15-20B → FLOPs 接近 15-20B Dense 模型

实际使用场景:
  主要通过 Google Cloud API 使用（不自部署）
  API 支持 1M 上下文，适合:
  - 完整代码库分析
  - 整本书/整篇论文处理
  - 长视频 + 音频 + 文本的联合理解

成本:
  API 定价: $1.25-3.50/1M tokens（取决于版本）
  比 GPT-5.5 便宜，比 DeepSeek V3 贵

它的优势从何而来​

优势根源
1M+ 上下文滑动窗口 Attention + 分块 KV Cache + MoE 降低开销
原生多模态统一 token 空间，跨模态 attention 自然交互
推理 benchmark 领先3-7.5T 总参数的知识容量 + Meta-Controller 自编排
科学/研究能力强长上下文 + 多模态 + 大参数的综合效果

Claude Opus 4.8 — Dense 架构的编码王者​

架构规格​

项目信息
架构Dense Transformer
上下文窗口200K tokens（标准）/ 1M（Opus 4.8 新增）
推理模式混合（标准 + Extended Thinking）
训练方式Constitutional AI + RLHF
定价$5/1M input, $25/1M output

为什么 Dense 还能打​

在 MoE 大行其道的 2026 年，Claude 坚持 Dense 架构但有独特优势：

Dense 架构对编码任务的优势:

1. 参数一致性:
   每个 token 经过相同的路径 → 代码理解和生成更一致
   MoE 模型: 不同 token 可能经过不同 Expert
   → 代码生成可能出现"风格跳跃"

2. 指令跟随稳定性:
   Dense 模型对复杂指令的理解路径一致
   多步骤、多约束的编码指令 → Dense 更可靠

3. Extended Thinking 的天然适配:
   Thinking 模式下，模型生成的推理链也需要被后续步骤关注
   Dense 架构下，所有推理步骤使用同一组参数
   → 推理链的连贯性更好

4. 安全边界:
   Constitutional AI 训练在 Dense 架构下更可控
   → 代码安全性（如不生成漏洞代码）更有保证

Extended Thinking 的机制​

Claude 的 Extended Thinking:
  用户输入 → 模型生成思考链（最多 32K thinking tokens）→ 生成最终答案

实现方式:
  思考链作为 prefix tokens 被添加到上下文中
  最终答案生成时，可以 attend 到思考链的每一个 token
  思考链对用户可选展示（可隐藏或流式展示）

与 DeepSeek R1 的区别:
  R1: 内置思维链，用户无法控制思考深度
  Claude: 通过 API 参数控制最大 thinking tokens
  → 更灵活：简单问题不需要长思考，复杂问题可以深度推理

对部署的影响:
  Thinking tokens 也占用 KV Cache
  32K thinking + 500 answer tokens → KV Cache 比非 Thinking 模式大 60x+
  需要 Thinking Token 限制 + KV Cache 策略

部署视角​

Claude Opus 4.8 部署要点:

通过 Anthropic API 使用（不开源，不可自部署）

上下文窗口从 200K 扩展到 1M:
  1M 上下文的成本: token 消耗大幅增加
  建议: 只在需要完整代码库分析时使用 1M 模式
  日常对话使用 200K 模式

Fast Mode:
  Opus 4.8 的 Fast Mode 成本降低了 3x

面试视角​

常考问题​

  1. "DeepSeek V3 为什么能把价格做到这么低？"

    回答框架：

    • MoE 架构：671B 参数但仅激活 37B，推理 FLOPs 远低于 Dense
    • FP8 训练：用约 1/3 的 compute 量达到相近效果，训练成本大幅降低
    • MLA 注意力：KV Cache 压缩 30-50%，显存效率高
    • 256 个细粒度 Expert + Top-8 路由 → 专家专业化程度高

  2. "Llama 4 的 Top-1 路由为什么能工作？其他 MoE 不都是 Top-2 吗？"

    回答框架：

    • Shared Expert 始终激活，提供稳定的基础能力
    • 128 个 Expert 足够细粒度，每个 Expert 高度专业化
    • 交替 Dense + MoE 层的设计保证表达能力
    • Dense 层作为"安全网"，防止 MoE 路由失误导致的质量下降

  3. "Qwen3.5 的混合注意力是什么？它还是 Transformer 吗？"

    回答框架：

    • 不是纯 Transformer 了
    • 混合了 Gated DeltaNet（线性注意力，O(N) 复杂度）和 Gated Attention（标准注意力）
    • 门控网络动态决定每层用哪种注意力
    • 长上下文推理速度提升 3-5x，计算效率提升 ~80%

  4. "MoE 模型做 Agent 比 Dense 模型好吗？为什么？"

    回答框架：

    • MoE 的 Expert 天然就是"专业化子网络"，不同任务路由到不同 Expert
    • 任务间干扰小（Expert 隔离），Dense 模型所有任务共享同一组参数
    • 1T 总参数提供足够的"专业知识储备"
    • 但要注意：MoE 的延迟不如 Dense 可预测，Agent 场景中对延迟的要求需要权衡

  5. "Gemini 3 Pro 的 100 万 token 上下文是怎么实现的？"

    回答框架：

    • Attention 计算：不能用 O(N^2) 的标准 Attention，可能用了滑动窗口 Attention + 全局 Memory Tokens，或 Linear Attention 变体
    • KV Cache：分块管理，近期 token 全缓存，远距离 token 压缩
    • 位置编码：标准 RoPE 在 1M+ 长度下精度下降，可能用了扩展 RoPE 或专用长距离方案
    • MoE 架构降低层间通信开销，使大模型在大上下文下可行
