解剖 Claude Code：一次完整任务日志背后的 6 个工程秘密

2026年6月3日

模型本身是不可靠的。让 Claude Code 看起来"可靠"的，不是模型，是一层又一层的工程机制。

起因​

Claude Code 用起来很顺：输入指令，等它写代码，跑测试，提交。整个过程像是一个靠谱的同事在干活。

但如果你把它当作"一个 prompt 发过去，LLM 直接吐代码"，那就完全想错了。

一次偶然的机会，我完整记录了一次 Claude Code 任务执行过程中，它与后端 LLM 之间的全部交互日志。从用户输入的第一条指令，到最终代码提交，中间经历了什么、模型看到了什么、工具如何被调用和调度，全部暴露无遗。

这篇文就是从那堆日志里蒸馏出来的东西。不是概念，不是最佳实践，是实打实的工程机制。

一、同时说三件事，它怎么保证不漏​

大多数人在用 Claude Code 时都干过这种事：

帮我把这个项目跑起来：创建虚拟环境，装依赖，然后跑测试看看有没有问题

一句话，三件事。换一个人来，也可能漏掉其中一步。对一个会截断、会输出格式错误的 LLM 来说，执行三个独立指令的挑战更大。

日志里发生的事情：

Claude Code 没有把这句话直接扔给模型，而是先在本地做了一个指令分割——把用户的自然语言拆成三个独立的任务单元：创建环境、安装依赖、运行测试。每个单元有明确的开始和结束标记，彼此隔离。

更关键的是接下来的机制：JSON 完整性保证。

Claude Code 要求模型以结构化格式（JSON）输出每个工具调用。但 LLM 的输出可能被截断（token 限制、网络波动），导致 JSON 不完整。Claude Code 维护了一个 JSON 缓冲区——它不会在收到模型输出后立即执行，而是先验证 JSON 是否完整。如果不完整，它会发起一个补全请求，让模型把缺失的部分补齐，而不是直接失败。

这个机制看起来微不足道，但它是可靠性的基石。模型本身不可靠（可能截断、可能格式错误），工具层必须做校验和补全。这也是为什么你在用 Claude Code 时，很少看到"因为输出格式错误而任务失败"的情况——不是模型不会犯错，是工具层兜住了。

二、上下文越来越长时，它删了什么、留了什么​

一个典型的 Claude Code 任务，上下文会快速膨胀。写一个功能需要读文档、读代码、看测试结果、看错误日志——几轮下来，上下文就逼近了模型的窗口限制。

Claude Code 怎么处理？

直观的想法是"截断旧的，保留新的"。日志显示的做法更精细：语义压缩。

它不是简单地删除最早的对话，而是做了两件事：

第一，保留决策点，删除推理过程。 模型之前"为什么选了 A 方案而不是 B 方案"这个结论会被保留，但推导过程会被压缩成一句话摘要。因为后续执行需要知道"当前用的是 A 方案"，但不需要重新看一遍 A 和 B 的对比分析。

第二，生成进度快照。 每次压缩时，Claude Code 会生成一个结构化的快照：当前状态（正在做什么）、已完成项（做了什么）、待办项（还要做什么）、阻塞项（在等什么）。这个快照作为压缩后上下文的"锚点"，模型以此为起点继续推理。

这解决了一个经典问题：模型可能忘记"做了什么"，但只要记得"为什么这么做"和"现在进行到哪"，就能保持一致性。

决策理由的保留比决策结果本身更重要。这一点在长任务中尤为关键。

三、工具不是全给你的​

你可能觉得 Claude Code 每次都会把所有可用工具都告诉模型。日志显示的恰恰相反：动态工具路由。

Claude Code 会根据当前任务阶段，选择性地呈现工具：

  • 在读取代码阶段，文件操作工具（Read、Glob、Grep）优先级最高
  • 在写代码阶段，Edit、Write 工具被激活
  • 在验证阶段，Bash 工具（跑测试、编译）被优先呈现
  • 不相关的工具会被隐藏或者降级

更细致的是，每个工具的描述中包含了使用约束。比如某个工具的描述会明确标注"这个工具只能读，不能写"，而不是简单地说"这是一个文件读取工具"。

这种做法的好处很直接：工具列表越长，模型混淆和错误调用的概率越高。不是给模型"所有能力"，而是给模型"当前需要的能力"。这和操作系统按需加载页面而非一次性加载全部内存的思路是一样的。

四、System Prompt 不是一个大段落​

Claude Code 的 System Prompt 有清晰的层次结构，日志中可以看到四个层次：

身份层在最上面——"你是一个编程助手，你的目标是帮助用户完成代码任务"。这层定义了角色。

规则层紧随其后——"先思考再行动"、"不确定的事情问用户"、"不要运行破坏性操作"。这层定义了行为边界。

工具层列出了当前阶段可用的工具以及每个工具的契约（输入、输出、约束）。这层定义了能力。

格式层在最下面——"你的输出必须遵循以下 JSON schema"。这层定义了交互协议。

这种分层设计有两个好处：一是模型更容易理解自己的角色边界（每一层负责不同的约束类型），二是为 CLAUDE.md 这类自定义配置文件留出了精确的注入点——它补充的是规则层的内容，而不是去改身份层或工具层。

五、你看到的流式输出和实际执行是两回事​

用 Claude Code 时，你会看到 token 一个字一个字地冒出来。直觉上会觉得这是"模型一边想一边输出"。

日志揭示了一个更有趣的机制：流式输出和工具执行是解耦的。

当模型输出一个"计划"（接下来要做 A、B、C 三件事）时，Claude Code 会做两件事：

第一，把"正在做什么"的进度信息流式输出给用户，让你知道系统在工作，而不是对着一个白屏等。

第二，在后台解析这个计划，如果 A、B、C 之间没有依赖关系，就并行执行。三个独立的文件读取操作可以同时进行，不需要等第一个读完再读第二个。

流式输出的核心价值不是"让用户看到 token 逐字出现"，而是让用户知道系统正在工作，同时后台最大化并行度。这两件事拆开来看，每一件都不难，但组合在一起才是好的用户体验。

六、压缩之后，模型怎么不迷路​

这是第二部分的补充，但值得单独拎出来说。

上下文压缩最大的风险是"模型迷路"——删了太多东西，模型不知道现在进行到哪、之前做了什么决定、为什么这么决定。

Claude Code 的解法是摘要 + 锚点策略：

摘要概括已完成的工作（"已经创建了 3 个文件：app.py、config.yaml、test_app.py"），锚点标记当前进度（"现在正在修复 test_app.py 中的断言错误"）。

更重要的是，锚点中包含了关键的决策理由：

决策：选择 pytest 而非 unittest
理由：项目已有 pytest 依赖，且团队偏好 fixture 模式

这个决策理由被保留在压缩后的上下文中。模型在后续执行中如果遇到了测试相关的问题，它会基于"团队偏好 fixture 模式"这个理由做出一致的决策，而不是随机选择另一种方案。

这其实触及了 AI 编程工具的一个深层设计原则：一致性不来自于记忆完整，而来自于决策理由的可追溯性。模型可以忘记很多细节，但决策理由必须在。

总结：工程机制决定可靠性​

这 6 个发现可以归结为一句话：Claude Code 的竞争力不在于"用了多大的模型"，而在于工程机制的设计质量。

机制解决的问题
指令分割 + JSON 完整性多指令执行不漏不掉
语义压缩 + 进度快照长上下文不迷路
动态工具路由工具多了不混淆
System Prompt 分层角色边界清晰
流式输出 + 并行执行体验好且效率高
决策理由保留压缩后保持一致

模型提供了"理解"和"生成"的能力。但可靠性、效率、用户体验，全靠工具层的工程实现。

这也指向了一个更广泛的趋势：AI 应用的竞争力正在从"prompt engineering"转向"system engineering"。谁的工程机制设计得更好，谁的用户体验就更可靠。而可靠性，恰恰是 AI 编程工具从玩具变成生产力的分水岭。
