单 Agent 的天花板：为什么 Expert 到 Virtuoso 需要一支专家团队

2026年6月3日

一个 Agent 无法同时是 GPU 专家、网络专家、调度专家、安全专家。Virtuoso 级别的决策，不是单个专家能独立完成的。

三条 Scaling Law​

过去几年 AI 的发展可以被归结为三条曲线。

第一条是数据与参数的 Scaling——加大模型、加数据量。这是 2020 到 2024 年的主旋律，GPT-3 到 GPT-4、Llama 1 到 Llama 3 的故事都是这条曲线。但它已经进入了收益递减区：参量翻一倍，效果不再翻一倍。

第二条是推理的 Scaling——让模型"想得更深"。思维链、强化学习、Test-Time Compute 是 2024 到 2025 年的焦点。DeepSeek-R1、o1 系列都在走这条路。它仍在快速演进，但天花板可见——再想深下去，推理成本会指数级增长。

第三条是 Agent 的 Scaling——让模型与外部世界持续交互，从环境反馈中自我进化。这是当前和未来两三年的核心增长引擎。

为什么第三条最关键？因为前两条是在"提升单个模型的能力"，而第三条是在"构建一个能持续自我学习的环境"。单模型的天花板是硬的，自学习环境的天花板远得多。

而 Agentic Coding 恰好是第三条路线的第一块试验田。代码世界天然适合 Agent：环境确定（编译器告诉你行不行）、反馈即时（测试跑不跑得通）、试错成本低（改完再跑就是了）。一旦 Agent 在代码世界验证了"自主执行加环境反馈加自我进化"这条链路，它就具备了走向更广阔物理世界的资格。

卡住的那道门槛​

Google DeepMind 有一个 Levels of AGI 的框架，把 AI 系统的能力分成几个等级。当前最前沿的系统在代码、写作、数据分析这些结构化领域已经到达了 Expert 级别——达到第 90 百分位人类专家的水平。

但从 Expert 到 Virtuoso（第 99 百分位）的跃迁，卡住了。

卡住的原因不是模型不够大、推理不够深。卡住的原因是一个根本性的结构问题：Virtuoso 级别的决策，需要多个不同领域专家的协作寻优，而当前主流的架构是单 Agent 加单 Harness。

一个真实的例子：部署一个生产级的推理系统。这个任务需要 GPU 架构师评估型号和显存、网络工程师评估延迟和带宽、调度专家评估扩缩容策略、安全专家评估攻击面。在单 Agent 架构下，一个 Agent 要同时扮演这四个角色——它不可能在每一个领域都有 Virtuoso 级别的深度。

现实中的 Agent 表现清晰地反映了这道门槛的存在：从 Novice 到 Apprentice（写个脚本、查个 API）没问题，从 Apprentice 到 Expert（部署推理集群、搭建 RAG 系统）在特定领域能做到，但从 Expert 到 Virtuoso，那道跨领域协作的鸿沟，单 Agent 过不去。

不是"多加几个 Agent"​

当人们听到"多 Agent 协作"时，第一反应是"那不就是让几个 Agent 一起干活吗"。

不是那么简单。多 Agent 架构要解决的是一整套比单 Agent 复杂得多的问题。

拓扑结构怎么设计？ 是全连接（每个 Agent 都能和每个 Agent 通信）、星型（一个中心节点协调所有 Agent）、还是动态路由（根据任务需求临时建立通信路径）？拓扑结构直接决定了信息流动效率和决策质量。全连接的信息流动最充分但通信开销最大；星型的开销最小但中心节点是瓶颈；动态路由最灵活但需要一套复杂的路由决策机制。

什么时候派哪个 Agent 上场？ 不是所有任务都需要所有 Agent 参与。一个简单的代码审查可能只需要一个 Reviewer Agent，而一个系统架构决策可能需要多个领域 Agent 同时参与。调度策略决定了资源利用率和响应速度。

遇到新领域怎么办？ 系统不可能预先定义好所有可能的 Agent。当遇到一个从未处理过的问题域时，系统需要能够自动创建新的 Agent——给它定义角色、能力边界、工具集，然后让它加入协作网络。

这三件事——拓扑优化、调度优化、动态生成——构成了多 Agent 架构的核心挑战。它不是"多加几个 Agent"就解决的。

三层架构​

基于这些挑战，一个完整的多 Agent 架构需要三层。

第一层：协作的骨架​

这一层解决"多个 Agent 怎么协作"的问题。

Agent 数量的爆发是必然趋势。原因有三个：上下文隔离需要 Agent 分裂（按上下文边界切，不按问题类型切）、多视角决策寻优需要 Agent 扩增（多个 Agent 独立推理后综合，决策质量显著优于单 Agent 深度思考）、专精避免工具过载（单 Agent 持有超过 15 个工具时，调用正确率显著下降）。

这一层要做的就是管理这种爆发：定义 Agent 之间的通信协议、调度策略、以及按需生成新 Agent 的机制。

第二层：数据的骨架​

Agent 的智力不仅取决于模型能力，还取决于它能获取和理解数据的质量。

从原始的数据仓库到语义层（数据有了业务含义）再到本体层（Ontology，数据之间的关系被结构化定义）。关键是把数据从"可查询"变成"可推理"——Agent 不只是"查到某个 GPU 的显存是 80GB"，而是"推理出 80GB 显存对于 70B 模型的张量并行是否足够"。

第三层：运行时的骨架​

生命周期管理、资源调度与隔离、可观测性、安全治理。当 Agent 数量从几个变成几十个时，这一层的重要性指数级增长。

一个具体的场景​

假设要评估"是否应该把推理集群从 A100 迁移到 H100"这个决策。

在单 Agent 架构下，一个 Agent 需要自己去查 A100 和 H100 的规格、评估成本差异、考虑迁移风险、给出建议。它在每个领域都只能做到表面。

在多 Agent 架构下：

  • GPU 架构师 Agent 评估型号差异——H100 的 Transformer Engine 对推理吞吐的提升、显存带宽的变化
  • 网络拓扑 Agent 评估互联差异——NVLink 到 NVSwitch 的升级对多卡推理的影响
  • 调度优化 Agent 评估迁移策略——灰度迁移的方案、回滚路径、资源过渡期的分配
  • 最后由一个协调者做一致性校验——确保 GPU Agent 推荐的方案和网络 Agent 的评估不冲突

每个 Agent 在自己的领域做到 Virtuoso 级别，协调者确保跨领域的一致性。这就是 Expert 到 Virtuoso 的路径——不是让一个 Agent 变得更聪明，而是让多个专精 Agent 协作寻优。

现在能走到哪​

多 Agent 协作还在非常早期的阶段。开源生态中有 GPTSwarm、AutoGen、LangGraph 的 Multi-Agent 模式，但距离生产级还有一段距离。

最接近可用的方案是 LangGraph 的 Supervisor 加 Handoff 模式。它不是完整的集群架构，但已经能解决大部分跨领域协作的实际问题。

这个方向的终局不遥远——不是因为技术已经成熟，而是因为需求已经清晰：单 Agent 的天花板就在那里，Expert 到 Virtuoso 的那道门槛，靠的不是更大的模型，是更好的架构。
